# Build prompt for Rewind, a time-travel debugger for coding agents

Paste everything below this line into Replit Agent as the first message. You need a paid Replit plan for the managed model access.

---

You are building a full-stack app called Rewind on Replit. Rewind records a coding agent's session as a full trajectory and lets a user scrub back to any step, inspect the exact repo state and model context at that step, fork from that step with a different model or an edited prompt, and watch the new branch run beside the original. Branches render as a tree and any two leaves can be diffed.

Build it end to end in this order and do not skip ahead. Confirm each phase works before moving to the next. Ask me nothing until phase 1 is verified. Make reasonable decisions on anything unspecified and note them in a DECISIONS.md file at the repo root.

## Non-negotiable decisions

1. Deploy as a Reserved VM, app type Web server. Not Autoscale. Forks run for minutes and stream over SSE, so the process must stay alive.
2. Write our own agent loop. Do not install or wrap OpenCode, Claude Code, Aider, or any existing agent framework. The loop is a plain while loop over an OpenAI-compatible chat completions API with four tools. We own the message array. That is what makes recording and forking trivial.
3. Never rely on the published filesystem for persistence. The filesystem is scratch. All durable state lives in Postgres and Replit Object Storage.
4. The agent's shell access is whitelisted. It cannot run arbitrary commands. See the sandbox section.
5. Every step commits to git. A trajectory step without a commit hash is a bug.

- Database is Replit's built-in Postgres. Use SQLAlchemy with asyncpg. Migrations via Alembic.

- Auth is Replit Auth. Viewing sessions requires no login. Creating sessions and forking requires login.

- Git via subprocess calls to the git binary. Do not use GitPython.
- SSE for live events using sse-starlette.

## Data model

Postgres tables. Use UUID primary keys and timestamptz for all timestamps.

```
users
  id, replit_user_id (unique), username, created_at

repos
  id, slug (unique), name, description, bundle_key (object storage key of the base git bundle), created_at

sessions
  id, user_id (nullable for seeded sessions), repo_id, title, root_branch_id, created_at

branches
  id, session_id, parent_branch_id (nullable), fork_step_index (nullable, the step in the parent this branch was forked from),
  model_id, system_prompt, task_prompt, status (queued | running | done | failed | cancelled),
  step_count, total_input_tokens, total_output_tokens, bundle_key (nullable until the branch finishes), created_at, finished_at

steps
  id, branch_id, index (0-based, unique per branch), kind (user | assistant | tool_call | tool_result),
  content (jsonb, the exact message object as sent to or received from the model),
  tool_name (nullable), tool_args (jsonb nullable), tool_result (text nullable, truncated to 20k chars),
  commit_hash (nullable for user and assistant kinds, required for tool_result kinds where the tool mutated files),
  files_changed (jsonb array of paths), input_tokens, output_tokens, latency_ms, created_at
```

A branch's message array at step k is the ordered content of steps 0..k. That is the entire context the model saw. Store it exactly as sent, no summarization.

## Agent loop

File backend/agent/loop.py. One function run_branch(branch_id) that runs as an asyncio task and publishes events to an in-process pubsub keyed by branch_id.

Loop shape

```
messages = [system, user_task] (or the sliced parent messages when forking, see below)
while step_count < MAX_STEPS and not cancelled:
    response = chat.completions.create(model, messages, tools, stream=False)
    record assistant step
    if no tool calls: mark done, break
    for each tool call:
        result = execute(tool)
        if tool mutated files: git add -A and git commit -m "step {n}: {tool_name} {short args}"
        record tool_result step with commit hash and files_changed from git diff --name-only HEAD~1
    append assistant and tool messages to messages
```

Tools, with strict JSON schemas passed to the model

- read_file(path) returns the file contents. Path must be inside the worktree.
- write_file(path, content) creates or overwrites. Path must be inside the worktree.
- edit_file(path, old_string, new_string) replaces exactly one occurrence. Error if zero or multiple matches.
- run(command) executes a whitelisted command only. See sandbox.

System prompt is short and fixed. State the tools, tell the model to finish by replying without tool calls when the task is complete, and tell it to run the test command before finishing.

Limits, all read from environment with these defaults. MAX_STEPS 30. MAX_OUTPUT_TOKENS_PER_CALL 4000. MAX_TOTAL_TOKENS_PER_BRANCH 150000. WALL_CLOCK_SECONDS_PER_BRANCH 600. When any limit hits, mark the branch failed with a reason and commit whatever is on disk.

Cancellation. A branch can be cancelled via the API. The loop checks a cancellation flag before every model call and before every tool call.

Concurrency. At most 4 branches run at once per VM. Others queue. Expose queue position in the branch status.

## Worktrees and git

Each branch gets its own directory at /tmp/rewind/branches/{branch_id}. Create it by restoring the repo's base bundle, then if the branch is a fork, checking out the parent's commit at fork_step_index.

Commit identity is fixed to name Rewind and email rewind@localhost. Set it per repo, not globally.

When a branch finishes, failed or done, run git bundle create on the full branch history, upload it to object storage under bundles/{branch_id}.bundle, store the key on the branch row, and delete the worktree. When a user opens a step later, restore that bundle into a fresh temp dir, check out the step's commit, and serve files from there. Cache restored worktrees for 10 minutes then delete.

File contents for the viewer come from git show {commit}:{path}. Never read from the live worktree of a running branch for the viewer, always from git, so the scrubber shows the state at exactly that commit.

## Fork semantics

POST /api/branches/{id}/fork with body { step_index, model_id, edited_task_prompt (optional), count (1 to 5, default 1) }.

For each requested fork
1. Create a branch row with parent_branch_id and fork_step_index.
2. Build messages as the parent's steps 0..step_index inclusive. If the last included step is a tool_call kind without its tool_result, exclude it so the array ends at a valid boundary. If edited_task_prompt is given, replace the content of the first user message.
3. Find the last commit_hash at or before step_index in the parent. Restore the parent's bundle (or copy its live worktree if still running, then git checkout that commit).
4. Enqueue run_branch.

count 5 with the same model and prompt is the divergence experiment. It must work.

## Sandbox

The run tool accepts only commands that match one of the repo's whitelisted commands, stored in a file named .rewind.json at the repo root, for example

```
{ "test": "python -m pytest -q", "lint": "ruff check ." }
```

The model calls run("test") or run("lint"). Any other string returns an error message to the model and is recorded. Commands execute with cwd set to the worktree, a 60 second timeout, stdout and stderr captured and truncated to 20k chars, and an environment containing only PATH, HOME set to the worktree, and PYTHONDONTWRITEBYTECODE. Path arguments to read_file, write_file, and edit_file are resolved and rejected if they escape the worktree. Reject symlinks.

Rate limits. A logged-in user can create at most 10 branches per hour. Anonymous users cannot create branches.

## API

```
GET  /api/repos                                  list seed repos
GET  /api/sessions                               list sessions, newest first, with branch counts
POST /api/sessions                               { repo_id, title, task_prompt, model_id } creates session and root branch, starts it. Auth required.
GET  /api/sessions/{id}                          session with full branch tree (branches with parent ids, status, step_count, fork_step_index)
GET  /api/branches/{id}/steps                    all steps for a branch, ordered
GET  /api/branches/{id}/steps/{index}/files      file tree at that step's commit, with changed paths flagged
GET  /api/branches/{id}/steps/{index}/file?path= file content at that step's commit
GET  /api/branches/{id}/steps/{index}/context    the exact messages array the model saw at that step
GET  /api/diff?a={branch_id}:{step}&b={branch_id}:{step}   unified diff between two commits, plus list of changed files
POST /api/branches/{id}/fork                     see fork semantics. Auth required.
POST /api/branches/{id}/cancel                   Auth required, owner only.
GET  /api/branches/{id}/events                   SSE stream of step events for a running branch. Replays existing steps first, then streams new ones.
GET  /api/me                                     current user or null
```

SSE event shape is { type: "step" | "status", data: step row or branch status }.

## Frontend

Three pages.

Home. List of sessions as cards showing title, repo, model, branch count, and a tiny inline tree sketch. A New session button that opens a form with repo dropdown, task prompt textarea, model dropdown. Anonymous users see the list and a Log in to fork prompt.

Session page, the core of the app. Layout is three panes.

- Left pane, branch tree. Each branch is a node. Root at top. Forks hang off their parent at the fork step. Nodes show model id, status badge, step count. Running branches pulse. Clicking a node selects it. Shift-click a second node to enter diff mode.
- Center pane, timeline scrubber plus step detail. A horizontal scrubber across the top with one tick per step, colored by kind. Drag or use arrow keys to move. Below it, the selected step rendered as a card. Assistant steps show the text. Tool calls show name and args. Tool results show output in a monospace block. A Context button opens a drawer with the full messages array at that step, rendered as collapsible message cards, with a token count.
- Right pane, file tree and viewer at the selected step's commit. Changed files at that step are highlighted. Clicking a file opens it in Monaco read-only. A Diff vs previous step toggle shows the change that step made.

Fork control. A Fork here button on the scrubber opens a popover with model dropdown, an editable task prompt prefilled from the branch, and a count selector 1 to 5. Submitting creates the branches and they appear in the tree immediately as queued, then stream in live.

Diff mode. With two nodes selected, the center pane becomes a two-column diff of the two leaves' final commits (or the selected steps if the user picked specific steps), with a changed-files list on the left and Monaco diff editor on the right.

Live updates. When a branch is running, subscribe to its SSE stream. New steps append to the scrubber in real time. If the user is parked on the latest step, follow along. If they scrubbed back, do not yank them forward.

Keyboard. Left and right arrows move one step. Home and End jump. F opens fork popover. D toggles diff mode.

Mobile. Stack the panes vertically. Do not spend much time here.

Visual style. Dark, dense, monospace for code, a single accent color. This is a debugger. No marketing hero, no gradients, no emoji.
